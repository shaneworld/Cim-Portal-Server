# AP1 IT CIM Portal — 生产部署与运维手册

> 适用环境:**Linux 主机 + Nginx + systemd**,**Oracle 数据库**,**公司 SSO(OIDC)**。
> 本手册覆盖四大主题:**① 运行 · ② 数据库连接 · ③ SSO 配置 · ④ 部署**,以及上线检查、运维与排错。
> 简版速查见同目录 `部署指南-Linux.md`;本文件为完整版。

---

## 一、总体架构

```
                         ┌──────────────────────── Linux 应用主机 ────────────────────────┐
  用户浏览器 ─443/TLS──▶ │ Nginx ─┬─ /                → /var/www/cim-portal(SPA 静态文件) │
                         │        └─ /api  /actuator  → http://127.0.0.1:8080(反向代理)   │
                         │                                      │                          │
                         │             portal.jar(systemd,profile=prod,仅绑 127.0.0.1)   │
                         │                                      │ ojdbc11(JDBC)            │
                         └──────────────────────────────────────┼──────────────────────────┘
                                                                 ▼
                                                       外部 Oracle 数据库
  用户浏览器 ─443──▶ 公司 SSO(OIDC IdP)  ◀────── JWKS 公钥拉取 ────── portal.jar
```

- **前端**:Vue 3 单页应用(SPA),Vite 构建为静态文件,由 Nginx 直接服务。
- **后端**:Spring Boot 3.3(JDK 21)无状态 OAuth2 资源服务器,打包为 `portal.jar`,以 systemd 服务运行,**只监听 `127.0.0.1:8080`**,不直接对外。
- **同源**:SPA 与 API 经同一个 Nginx 域名访问,因此**不需要 CORS**。
- **数据库**:外部 Oracle;后端启动时由 Flyway 自动建表/迁移(V1–V6)。
- **认证(双签发方 JWT)**:
  - **公司 SSO**:浏览器用 OIDC Authorization Code + PKCE 登录,拿到 IdP 签发的 token;后端用 `MultiIssuerJwtDecoder` 按 `iss` 路由,从 IdP 的 JWKS 端点拉公钥校验。
  - **内部账号(回退)**:SSO 不可用时,用工号 + 初始密码登录 `/api/auth/login`,后端用**门户自有 RSA 密钥**签发 `iss=cim-portal` 的 token。
  - 两类 token 的**授权**都来自本地 `user_info` 表(工号 → 部门/角色)。

## 二、前置条件

### 2.1 应用主机(Linux)
| 项 | 要求 |
|---|---|
| JDK | **21**(Temurin/Adoptium 等),`java -version` 可用 |
| Nginx | 已安装,可 `nginx -t` / `systemctl reload nginx` |
| openssl | 生成门户签名密钥 |
| 域名 + 证书 | 一个对内/对外域名,以及该域名的 TLS 证书与私钥(或用 certbot 签发) |
| 网络 | 主机可访问 **Oracle**(默认 1521)与**公司 SSO IdP**(HTTPS,用于 JWKS/discovery) |

### 2.2 构建机
JDK 21 + Maven、Node.js LTS(`npm`);`cim-portal-server` 与同级目录 `cim-portal-client` 两个仓库。

### 2.3 外部依赖(需提前向相关团队申请)
- **Oracle**:连接地址(host/port/服务名)、一个具备建表权限的账号/schema。
- **公司 SSO**:在公司 IdP 注册一个 OIDC 客户端(详见第七章),拿到 **Issuer URI**、**Client ID**,确认用户名所在的 **claim**。
- **用户数据**:门户授权依赖本地 `user_info`(工号、部门、角色),需约定同步/导入方式。

cd cim-portal-server

```
脚本会:① `mvn package` 生成后端 `portal.jar`;② `npm ci && npm run build` 生成前端 `dist/`(**`VITE_API_BASE_URL` 留空 → 同源**);③ 打包。产物:

```

  └─ release/
       portal.jar          → 部署到 /opt/cim-portal/portal.jar
       web/                 → 部署到 /var/www/cim-portal/
       deploy/              → systemd unit、nginx 配置、密钥脚本、示例配置

把 `cim-portal-release.tar.gz` 拷贝到应用主机并解压。

## 四、数据库连接与初始化(Oracle)

### 4.1 账号 / Schema / 权限
门户用一个独立 schema(账号)。Flyway 会在该 schema 内建表,因此账号需要建表/序列权限与表空间配额。由 DBA 执行(示例):

```sql
CREATE USER cim_portal IDENTIFIED BY "<强密码>";
GRANT CREATE SESSION, CREATE TABLE, CREATE SEQUENCE TO cim_portal;
ALTER USER cim_portal QUOTA UNLIMITED ON USERS;   -- 或指定业务表空间
```
> 若公司规范禁止应用账号建表,可让 DBA 预先按迁移脚本建好对象,并把 Flyway 设为校验模式;默认方案是让应用账号自行迁移(最简单)。

### 4.2 JDBC 连接串格式
后端用 Oracle Thin 驱动(`oracle.jdbc.OracleDriver`,自动识别)。常见写法:

| 形式 | URL |
|---|---|
| **EZConnect(服务名,推荐)** | `jdbc:oracle:thin:@//db-host:1521/PDB_SERVICE` |
| SID(老式) | `jdbc:oracle:thin:@db-host:1521:ORCL` |
| TNS 完整描述 | `jdbc:oracle:thin:@(DESCRIPTION=(ADDRESS=(PROTOCOL=TCP)(HOST=db-host)(PORT=1521))(CONNECT_DATA=(SERVICE_NAME=PDB_SERVICE)))` |
| RAC / SCAN | 用 SCAN 主机名作为 HOST,服务名作为 SERVICE_NAME |

> **服务名 vs SID**:多租户(CDB/PDB)环境用**服务名**(`//host:port/service`)。向 DBA 确认用的是服务名还是 SID。
> **TLS/钱包(如启用)**:URL 改用 `(PROTOCOL=TCPS)` 并配置 `oracle.net.wallet_location` 等 JVM 参数(写到 `portal.env` 的 `JAVA_OPTS`);非加密内网可忽略。

### 4.3 在配置文件中填写数据源
连接信息写入主机上的 `/etc/cim-portal/application-prod.yml`(机密文件,见 5.3):
```yaml
spring:
  datasource:
    url: "jdbc:oracle:thin:@//db-host:1521/PDB_SERVICE"
    username: "CIM_PORTAL"
    password: "<强密码>"
```

### 4.4 Flyway 自动建表与迁移
后端启动时自动执行 `classpath:db/migration/oracle` 下的迁移(Hibernate `ddl-auto=validate`,**所有 DDL 由 Flyway 负责**):

| 版本 | 作用 |
|---|---|
| V1 | 基础 schema(链接、枚举值、用户信息等) |
| V2 | 删除 label |
| V3 | 链接去除 code、增加多环境 URL |
| V4 | 链接环境属性(DEV/UAT/RELEASE) |
| V5 | 启动本地应用类型(launch_app + download_url) |
| V6 | `security_setting` 表(SSO 配置 + 内部密码),并种入一行默认配置 |

启动日志出现 `Successfully applied N migrations ... now at version v6` 即成功。**升级**只需替换 jar 重启,新迁移自动应用(Flyway 幂等,已应用的不再重复)。

### 4.5 用户数据置备(`user_info`)
门户的**授权**(谁是管理员、属于哪个部门)来自本地 `user_info` 表(生产**不**种入演示用户)。关键字段:

| 列 | 说明 |
|---|---|
| `employee_id` | 工号(主键)。**必须与 SSO token 中用户名 claim 的值一致**(见 7.4) |
| `display_name_zh` / `display_name_en` | 中/英文显示名 |
| `department_code` | 部门编码(对应枚举) |
| `role_code` | 角色编码;管理员用 **`PORTAL_ADMIN`**,普通用户用普通角色 |
| `email` | 邮箱 |
| `active` | 1=启用,0=停用(停用则无法登录) |
| `synced_at` | 同步时间 |

置备方式(任选其一,通常由 IT 定期同步):
- HR/AD 同步脚本批量写入;
- DBA 手工 `INSERT`;
- 上线初期至少插入**一个管理员**(`role_code='PORTAL_ADMIN'`, `active=1`),用于完成 SSO 配置:
```sql
INSERT INTO user_info (employee_id, display_name_zh, display_name_en,
                       department_code, role_code, email, active, synced_at)
VALUES ('ADMIN1', '系统管理员', 'Admin', 'IT', 'PORTAL_ADMIN', 'admin@corp.com', 1, SYSTIMESTAMP);
COMMIT;
```

### 4.6 连接验证
后端启动后:
```bash
curl -s http://127.0.0.1:8080/actuator/health     # {"status":"UP"} 表示含 DB 在内健康
```
若启动即报数据源/Flyway 错误,见第十章。

## 五、后端运行(systemd)

### 5.1 目录与专用用户(以 root 执行)
```bash
useradd --system --no-create-home --shell /usr/sbin/nologin cimportal || true
install -d -o cimportal -g cimportal /opt/cim-portal      # 放 portal.jar
install -d /var/www/cim-portal                            # 放前端
install -d -m 700 /etc/cim-portal                         # 放机密配置 + 密钥
install -o cimportal -g cimportal -m 644 release/portal.jar /opt/cim-portal/portal.jar
```

### 5.2 门户签名密钥(必须,且需备份)
内部账号登录签发的 token 用一对 **RSA 密钥**签名。生产必须提供**稳定**密钥,否则后端会用临时密钥(每次重启失效,日志有 WARN)。生成一次:
```bash
release/deploy/gen-portal-jwt-key.sh /etc/cim-portal
chown root:cimportal /etc/cim-portal/portal-jwt-*.pem
# 生成 portal-jwt-private.pem(600)与 portal-jwt-public.pem
```
> **务必备份私钥**:丢失会使所有已签发的内部 token 失效(用户需重登)。该密钥**只影响内部账号回退**,不影响 SSO。

### 5.3 运行配置 `application-prod.yml`(机密,不入库)
```bash
cp release/deploy/application-prod.example.yml /etc/cim-portal/application-prod.yml
chown root:cimportal /etc/cim-portal/application-prod.yml && chmod 640 /etc/cim-portal/application-prod.yml
```
内容与逐项说明:
```yaml
server:
  address: 127.0.0.1     # 只监听本机,由 Nginx 反代;不要改成 0.0.0.0
  port: 8080
spring:
  datasource:
    url: "jdbc:oracle:thin:@//db-host:1521/PDB_SERVICE"   # 见 4.2
    username: "CIM_PORTAL"
    password: "<强密码>"
app:
  security:
    portal-jwt:
      private-key-location: /etc/cim-portal/portal-jwt-private.pem   # 见 5.2
      public-key-location:  /etc/cim-portal/portal-jwt-public.pem
```
> **配置加载**:systemd 用 `--spring.config.additional-location=file:/etc/cim-portal/` 加载该文件,优先级高于 jar 内置的 `application.yml`,因此这里填的值会覆盖默认。SSO 相关配置**不在这里**,而在数据库 `security_setting`(运行时可改,见第七章)。

### 5.4 安装并启动服务
```bash
cp release/deploy/cim-portal.service /etc/systemd/system/cim-portal.service
# (可选)JVM 调优:cp release/deploy/portal.env.example /etc/cim-portal/portal.env
systemctl daemon-reload
systemctl enable --now cim-portal
journalctl -u cim-portal -f          # 跟踪启动日志(Ctrl-C 退出)
```
启动成功的标志(日志中):
- `Portal JWT: loading RSA key pair from files ...`(**不应**出现 ephemeral 临时密钥 WARN);
- Flyway `now at version v6`;
- `Started CimPortalApplication`。

服务以 `cimportal` 用户运行,`Restart=on-failure`,日志进 journald(`journalctl -u cim-portal`)。

## 六、前端与 Nginx(TLS 终止 + 同源)

### 6.1 部署静态文件
```bash
cp -r release/web/. /var/www/cim-portal/
```

### 6.2 站点配置
```bash
cp release/deploy/nginx/cim-portal.conf /etc/nginx/sites-available/cim-portal.conf
# 编辑:server_name=真实域名;ssl_certificate / ssl_certificate_key=真实证书路径
ln -sf /etc/nginx/sites-available/cim-portal.conf /etc/nginx/sites-enabled/cim-portal.conf
nginx -t && systemctl reload nginx
```
该配置要点:443 终止 TLS;`80 → 443` 跳转;`root /var/www/cim-portal`;**SPA 路由回退** `try_files $uri $uri/ /index.html`(刷新子路由不 404);`/api/` 与 `/actuator/health` 反代到 `127.0.0.1:8080`(透传 `X-Forwarded-*`);哈希资源长缓存、`index.html` 不缓存;安全响应头(HSTS / X-Content-Type-Options / X-Frame-Options / Referrer-Policy);gzip。

### 6.3 证书
- 公司签发:把 `fullchain.pem` / `privkey.pem` 放到配置里写的路径。
- 或 certbot:`certbot --nginx -d <域名>`(需 80 端口可达 + DNS 解析)。

## 七、公司 SSO(OIDC)配置

### 7.1 原理
- 前端是 **public client**,用 **Authorization Code + PKCE(S256)**,无 client secret。
- 前端启动时拉 `GET /api/portal/config` 得到 SSO 参数,据此初始化 OIDC 客户端。
- 登录成功后 IdP 把用户带回 **`https://<域名>/auth/callback`**,前端拿 token 调后端。
- 后端**不**预先连 IdP;收到 token 后按 `iss` 找到对应 IdP 的 JWKS 校验签名(运行时按 `security_setting` 里的 Issuer 解析,可热改)。

### 7.2 在公司 IdP 注册客户端
向 SSO 团队申请一个 OIDC 客户端,参数:

| 项 | 值 |
|---|---|
| 客户端类型 | **public**(SPA / 浏览器应用,无密钥) |
| 授权类型 | Authorization Code |
| PKCE | 必需,S256 |
| **Redirect URI** | `https://<域名>/auth/callback` |
| **Web Origin / CORS** | `https://<域名>`(允许浏览器从该源发起) |
| (可选)登出回调 | `https://<域名>/`(若启用 RP-initiated logout) |
| Scopes | 至少 `openid profile`(默认值) |

记录返回的 **Issuer URI**(形如 `https://idp.corp.com/realms/xxx` 或 `https://login.corp.com/...`,其 `/.well-known/openid-configuration` 可访问)与 **Client ID**;并确认**用户名所在 claim**(见 7.4)。

### 7.3 在门户填入 SSO 配置(运行时,无需重启)
两种方式,二选一:

**(A)管理页面**:用管理员账号登录后进入 **`/admin/security`**,填写并保存。

**(B)直接调 API**(`PUT /api/admin/security-settings`,需 `PORTAL_ADMIN` 的 Bearer token):
```bash
curl -X PUT https://<域名>/api/admin/security-settings \
  -H "Authorization: Bearer <管理员token>" -H "Content-Type: application/json" \
  -d '{
        "ssoEnabled": true,
        "issuerUri": "https://idp.corp.com/realms/xxx",
        "clientId":  "cim-portal-spa",
        "scopes":    "openid profile",
        "usernameClaim": "preferred_username"
      }'
```
字段对照(`security_setting` 表 / `SecuritySettingUpdateRequest`):

| 字段 | 含义 | 默认/种子值 |
|---|---|---|
| `ssoEnabled` | 是否启用 SSO(true 后登录页默认走 SSO) | `false` |
| `issuerUri` | IdP 的 Issuer(后端据此拉 JWKS;前端 `authority`) | 空 |
| `clientId` | 在 IdP 注册的 Client ID | 空 |
| `scopes` | 申请的 scope | `openid profile` |
| `usernameClaim` | token 中**等于工号**的 claim 名 | `preferred_username` |
| `initialPassword` | (仅内部账号回退用)重设全局初始密码,见 7.5 | 种子默认 `cimp@123` |

> 约束:`ssoEnabled=true` 时 `issuerUri`、`clientId` 不能为空(后端校验)。保存即生效,前端下次读取 `/api/portal/config` 即用新值。

### 7.4 用户名 Claim → 工号映射(关键)
后端从 token 取 `usernameClaim` 指定的 claim 值作为**工号**,再用它查 `user_info` 决定部门/角色:
```
employeeId = token.claims[usernameClaim]   // 取不到则回退到 sub
```
**因此 `user_info.employee_id` 必须与该 claim 的值完全一致**。请与 SSO 团队确认哪个 claim 承载工号(常见 `preferred_username`、`employeeId`、`upn` 等),把 `usernameClaim` 设成它。若用户在 IdP 能登录但门户提示无权限/查不到,多半是这里没对齐。

### 7.5 内部账号回退(SSO 不可用时)
- 登录页:`ssoEnabled=true` 时默认跳 SSO;**SSO 失败/不可用**时回落到内部登录页。
- 内部登录:`POST /api/auth/login`,body `{ "employeeId": "...", "password": "..." }`,成功返回门户签发的 `access_token`。
- 密码:**全局统一的初始密码**(非每人一个),存于 `security_setting.internal_password_hash`(BCrypt)。种子默认值为 **`cimp@123`**。
- **上线必做**:首次用管理员内部账号登录后,立刻通过 `/admin/security` 或 `PUT /api/admin/security-settings` 的 `initialPassword` 改成强密码。

### 7.6 端到端验证
```bash
# 公开配置(前端据此初始化)——启用后应返回 ssoEnabled=true 与 authority/clientId
curl -s https://<域名>/api/portal/config
```
浏览器打开 `https://<域名>/`:启用 SSO 后应自动跳转 IdP;登录后回到门户首页并能看到按权限过滤的链接卡片。

## 九、运维

### 9.1 升级
```bash
# 构建机重跑 deploy/build.sh,新包上传解压
install -o cimportal -g cimportal -m 644 release/portal.jar /opt/cim-portal/portal.jar
systemctl restart cim-portal           # Flyway 自动应用新迁移
cp -r release/web/. /var/www/cim-portal/ && systemctl reload nginx
```
建议升级前**备份数据库**(迁移会改结构)。

### 9.2 备份
| 对象 | 说明 |
|---|---|
| Oracle schema | 业务数据(链接、用户、配置),按公司 DBA 策略定期备份 |
| `/etc/cim-portal/portal-jwt-private.pem` | 门户私钥,**离线妥存**;丢失则内部 token 全失效 |
| `/etc/cim-portal/application-prod.yml` | 含 DB 口令,纳入机密管理 |

### 9.3 日志 / 健康 / 监控
- 日志:`journalctl -u cim-portal`(`-f` 跟踪,`-e` 跳到末尾,`--since "1 hour ago"`)。
- 健康:`/actuator/health`(经 Nginx `https://<域名>/actuator/health`,可供探活)。
- Nginx 访问/错误日志:`/var/log/nginx/`。

### 9.4 轮换
- **内部初始密码**:`/admin/security` 或 API 定期更换。
- **门户签名密钥**:如需轮换,重新 `gen-portal-jwt-key.sh` 并重启(会使旧内部 token 失效,需重登;不影响 SSO)。
- **SSO 客户端**:IdP 侧变更 Issuer/ClientID 后,在 `/admin/security` 同步更新即可,无需重启。

## 十、故障排查

| 现象 | 可能原因与排查 |
|---|---|
| 日志出现 *ephemeral 临时密钥* WARN | `application-prod.yml` 未配 `portal-jwt.*-key-location`,或 PEM 文件 `cimportal` 用户不可读 → 内部登录 token 重启即失效 |
| 启动报 数据源 / `ORA-` / Flyway 失败 | 连接串(服务名 vs SID)、账号口令、网络/防火墙到 1521;账号缺建表/序列权限或表空间配额;确认日志是否 `now at version v6` |
| `502 Bad Gateway` | 后端未起或未在 8080:`systemctl status cim-portal`、`journalctl -u cim-portal -e` |
| 刷新子路由 404 | Nginx 缺 `try_files ... /index.html`(SPA 回退) |
| 内部登录 401 | 工号不在 `user_info` 或 `active=0`;密码错(`/admin/security` 重设);确认走的是 `/api/auth/login` |
| SSO 跳转后报错/回不来 | IdP 未注册 `https://<域名>/auth/callback` 或 Web Origin;`/admin/security` 的 Issuer/ClientId 错;IdP 的 `/.well-known/openid-configuration` 主机不可达 |
| SSO 能登录但门户提示无权限/无数据 | `usernameClaim` 与工号未对齐(7.4),或该工号未置备到 `user_info` |
| 启用 SSO 保存失败 | `ssoEnabled=true` 时 `issuerUri`/`clientId` 不能为空 |
| 浏览器混合内容/CORS 报错 | 应为同源部署;确认前端构建时 `VITE_API_BASE_URL` 留空、且经 Nginx 同域访问 |
